## Логика работы сообщений в мессенджере

Этот документ описывает полный цикл обработки сообщений: от отправки пользователем до отображения у получателя.

# Общая архитектура

Пользователь А (отправитель)
│
▼
[ChatView] → [MessageFormComponent] → [sendMessage]
│
▼
[WebSocket: sendWS] → Бэкенд
│
▼
Бэкенд рассылает сообщение всем участникам чата
│
▼
[WebSocket: onmessage] у Пользователя Б (получатель)
│
▼
[handleIncomingMessage] → [RTK Query cache update]
│
▼
[MessagesList] автоматически перерисовывается

Поток данных: от отправки до получения

# Шаг 1: Инициализация WebSocket при старте приложения

При загрузке приложения выполняется цепочка:

StoreProvider → AuthSyncProvider → socketClient

1. StoreProvider монтируется первым, подписывается на изменения стора
2. При изменении currentUserId в сторе вызывается setWSCurrentUserId(userId) в socketClient
3. SocketClient сохраняет currentUserId в модульной переменной для использования в обработчиках

Важно: initWSHandlers(store.dispatch) вызывается до первого подключения сокета, чтобы wsDispatch был доступен в момент получения сообщений.

# Шаг 2: Отправка сообщения (отправитель)

Пользователь нажимает "Отправить" → срабатывает handleSend в MessageFormComponent:

2.1. Оптимистичное обновление кэша

// 1. Создаём временное сообщение с uid вида temp*123...
const optimisticMsg = { uid: `temp*${Date.now()}`, ... };

// 2. Добавляем его в кэш ДО ответа сервера
dispatch(
chatApi.util.updateQueryData(
'getMessages',
{ user_uid: queryUserUid, page_size: 30, ordering: '-created_at' },
draft => { draft.results.unshift(optimisticMsg); }
)
);

Пользователь сразу видит своё сообщение в интерфейсе.

2.2. Отправка через WebSocket
await sendMessage(chatUid, chatType, { content, files }, currentUserId, chatKey);

Функция sendMessage формирует payload:

{
action: 'create*text_message',
request_uid: 'uuid-...',
object: {
content: 'текст сообщения',
to_user_uid: 'UID*собеседника', // для личных чатов
// ИЛИ
chat_key: 'chat_123', // для групп
files: [...],
replied_messages: [...],
forwarded_messages: [...]
}
}

2.3. Отправка в сокет

sendWS подключает сокет (если нужно), добавляет коллбэк в pendingRequests по request_uid и отправляет JSON.

# Шаг 3: Обработка ответа от сервера (отправитель)

Бэкенд отвечает тем же request_uid:

// socketClient.ts → onmessage
const pendingCb = pendingRequests.get(response.request_uid);
if (pendingCb) {
pendingCb(response); // Разрешаем промис из sendWS
pendingRequests.delete(response.request_uid);
return;
}

Это подтверждает, что сообщение принято сервером. Оптимистичное сообщение остаётся в кэше, но может быть обновлено реальными данными при следующем запросе.

# Шаг 4: Получение сообщения другим пользователем

Бэкенд рассылает сообщение всем участникам чата через тот же action: 'create_text_message', но без request_uid (это не ответ на запрос, а событие).

4.1. Вход в handleIncomingMessage

if (response.action !== 'create_text_message') return;
if (!response.object) return;
if (!wsDispatch) return; // Защита от гонки инициализации

4.2. Определение queryUserUid для обновления правильного кэша
Ключевой момент: чтобы обновить кэш, нужно точно знать, под какими аргументами он был запрошен в useGetMessagesQuery.

// Извлекаем UID отправителя и получателя
const fromUid = rawMessage.from_user?.uid || rawMessage.from_user;
const toUid = rawMessage.to_user?.uid || rawMessage.to_user;

let queryUserUid: string | undefined;

// Группы/каналы: используем chat_key
if (rawMessage.chat_type !== 'chat' && rawMessage.chat_key) {
queryUserUid = rawMessage.chat_key;
}
// Личные чаты: используем UID СОБЕСЕДНИКА (не текущего пользователя!)
else if (rawMessage.chat_type === 'chat' || !rawMessage.chat_key) {
if (toUid && toUid !== currentUserId) {
queryUserUid = toUid; // Я получатель → обновляю по отправителю
} else if (fromUid && fromUid !== currentUserId) {
queryUserUid = fromUid; // Я отправитель → обновляю по получателю
}
}

Почему так? В личном чате user_uid в запросе — это всегда UID собеседника, а не ваш собственный. Бэкенд сам находит диалог между двумя пользователями.

4.3. Обновление кэша через RTK Query

wsDispatch(
chatApi.util.updateQueryData(
'getMessages',
{
user_uid: queryUserUid,
page_size: MESSAGES_PAGE_SIZE, // 30
ordering: MESSAGES_ORDERING // '-created_at'
},
draft => {
// Проверяем, нет ли уже такого сообщения в кэше
const exists = draft.results.some(m => m.uid === rawMessage.uid);

            if (!exists && rawMessage.uid) {
                // Маппим сырой ответ API в формат фронтенда
                const mapped = mapApiMessageToFrontend(rawMessage);
                // Добавляем в начало списка (новые сверху)
                draft.results.unshift(mapped);
            }
        }
    )

);

Критически важно: аргументы в updateQueryData должны точно совпадать с аргументами в useGetMessagesQuery в компонентах. Иначе кэш не найдётся, и сообщение не появится в интерфейсе.

# Шаг 5: Автоматический ререндер интерфейса (получатель)

1. updateQueryData меняет состояние кэша RTK Query
2. Компонент MessagesList, подписанный на useGetMessagesQuery(queryArgs), автоматически получает новые данные
3. React.memo и useMemo не блокируют обновление, потому что изменился объект data из хука
4. Список сообщений перерисовывается с новым сообщением вверху

Константы:

export const MESSAGES_PAGE_SIZE = 30;
export const MESSAGES_ORDERING = '-created_at' as const;

Эти константы используются в трёх местах:

1. chatApi.ts → getMessages.query → формирование параметров запроса к бэкенду
2. ChatView.tsx / MessagesList.tsx → аргументы для useGetMessagesQuery
3. socketClient.ts → аргументы для updateQueryData при получении сообщения

Если значения разойдутся хотя бы в одном месте (например, page_size: 30 в запросе и page_size: 50 в обновлении), кэш не совпадёт, и сообщение не появится в интерфейсе.

Правило: все параметры пагинации и сортировки для одного эндпоинта должны браться из одного источника.

Разница между личными чатами и группами

Личный чат (chat\*type === 'chat')

chatUid в пропсах компонента = UID собеседника

Запрос сообщений: GET /chat/message/text/{собеседник_uid}/

При получении: queryUserUid = UID\*отправителя (если я получатель)
В sendMessage: payload.object.to_user_uid = chatUid

Группа/канал (chat_type !== 'chat')

chatUid в пропсах = chat_key из ответа бэкенда (например, 'chat_5762')
Запрос сообщений: GET /chat/message/text/{chat_key}/

При получении: queryUserUid = rawMessage.chat_key

В sendMessage: payload.object.chat_key = chatKey

Обработка ошибок и откатов
Если отправка не удалась

try {
await sendMessage(...);
} catch (error) {
// Откат оптимистичного сообщения
dispatch(
chatApi.util.updateQueryData('getMessages', queryArgs, draft => {
draft.results = draft.results.filter(m => !m.uid?.startsWith('temp\_'));
})
);
// Показать уведомление пользователю
}

Если сокет отключился
socketClient автоматически пытается переподключиться до 5 раз с экспоненциальной задержкой. Все pendingRequests отклоняются с ошибкой при закрытии соединения.

Чеклист для разработчика
При добавлении нового параметра в запрос сообщений обновите его во всех трёх местах (api, компонент, socketClient)
Для личных чатов всегда передавайте user*uid = UID*собеседника, не свой
Проверяйте, что currentUserId установлен в socketClient до получения первого сообщения
Используйте константы MESSAGES_PAGE_SIZE и MESSAGES_ORDERING везде, не хардкодьте числа
При отладке сравнивайте queryUserUid в логах с user_uid в аргументах useGetMessagesQuery
