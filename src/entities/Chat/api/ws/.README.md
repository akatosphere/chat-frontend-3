## Схема работы: Изменение статуса прочтения сообщения

# Кратко

Пользователь проскроллил сообщение → фронтенд отправил запрос → бэкенд обновил БД → все участники чата мгновенно увидели изменение статуса (галочки ✓✓).

# Полная цепочка (7 шагов)

1️ Триггер на клиенте (Reader)
Что происходит: Пользователь Б проскроллил до сообщения в чате.
Как определяется:
IntersectionObserver видит, что сообщение появилось в области видимости
Проверяются атрибуты: data-is-new="true" + data-is-from-current-user="false"
Сообщение добавляется в очередь на отметку как "прочитанное"
Зачем очередь: Чтобы не слать 10 запросов при быстром скролле — они батчатся и отправляются одним пакетом через 300мс.

2️ Отправка запроса через WebSocket (Reader → Backend)
Что отправляется:
Action: change_status_read_message
Object: {
uid: "uuid-сообщения",
reader_uid: "uuid-читателя",
new_read_status: false, // ← false = "не новое" = прочитано
chat_key: "chat_123"
}

# Важно: Поле new_read_status: false означает "пометить как прочитанное". Это интуитивно неочевидно: false = "не новое" = "прочитано".

## Обработка на бэкенде

Что делает сервер:
Валидирует токены и права доступа
Находит сообщение по uid
Обновляет в БД: new: true → false для этого пользователя
Фиксирует время прочтения (опционально)
Что отправляет в ответ:

✅ Ответ инициатору: status: "OK" + объект сообщения с актуальным new: false

📢 Broadcast участникам: То же событие рассылается всем подключённым к этому чату (включая отправителя сообщения)

4️ Получение ответа на клиенте (Reader)
Что происходит:
Клиент получает status: "OK" → запрос считается успешным
Оптимистичное обновление уже сработало на шаге 1 → пользователь видит мгновенный отклик
Фоновый invalidateTags гарантирует, что при следующем запросе данные будут актуальными

5️ Получение broadcast на клиенте отправителя (Sender)
Что приходит:
Action: change_status_read_message
Object: {
uid: "uuid-сообщения",
new: false, // ← Сервер подтверждает: сообщение прочитано
...
}

# Как обрабатывается:

handleIncomingMessage ловит событие по action
Вычисляется targetUserUid (собеседник, чьи сообщения обновляем)
Находится кэш getMessages с нужными аргументами (user_uid, page_size, ordering)
В кэше ищется сообщение по uid (или по id для оптимистичных)
Поле new обновляется на false

6️ Обновление кэша и перерисовка (Sender)
RTK Query:
updateQueryData меняет данные в кэше → все компоненты, подписанные на этот запрос, получают новые данные
useGetMessagesQuery в useMessagesData автоматически пересчитывает messages
toLocalTextMessage вычисляет статус: msg.new === false → status: "READ"
MessageStatusNode рендерит иконку: status: "READ" → две синие галочки ✓✓
Важно: Компоненты не знают о WebSocket — они просто реагируют на изменение стейта. Это делает архитектуру предсказуемой.

7️ Синхронизация списка чатов
Параллельно обновляется:
Кэш getChats → превью последнего сообщения в списке чатов
Поле last_message.new → исчезает бейдж "1" у чата
Поле new_message_count → уменьшается счётчик непрочитанных
Результат: И в самом чате, и в списке чатов статус синхронизирован.

Ключевые моменты

Концепция | Почему это важно

new\*read_status: false = прочитано | Поле означает "является ли новым". false = "не новое" = прочитано. Не инвертируйте на фронте — доверяйте контракту.

Оптимистичное обновление | Меняем UI до ответа сервера → мгновенный отклик. Сервер потом подтверждает или откатывает.

Broadcast, а не только ответ | Отправитель сообщения тоже должен увидеть галочки. Без broadcast он узнает об изменении только после перезагрузки.

Поиск сообщения в кэше по uid || id | Оптимистичные сообщения имеют temp\*\* uid, но тот же числовой id. Ищем по обоим полям.

invalidateTags как страховка | Если кэш не нашёлся (сообщение на другой странице) — фоновый рефетч подтянет актуальные данные.

Изоляция хендлеров | Логика обработки WS вынесена в chatHandlers.ts → легко тестировать, не тянет за собой всё приложение.

## Синхронизация UI с WebSocket: Концепция для разработчиков

🎯 Главный принцип

# UI не подписывается на WebSocket напрямую.

# UI подписан на кэш RTK Query. WebSocket только обновляет этот кэш. Реактивность обеспечивает сама библиотека.

WebSocket → Обновление кэша → Авто-перерисовка компонентов

Поток данных (3 направления)
1️ Server → UI (Получение сообщений, статусы)
Сценарий: Пришло новое сообщение или изменился статус прочтения.

# Шаг | Что происходит | Кто отвечает

1 |Сервер шлёт событие через WS | Backend
2 | SocketClient ловит сообщение и передаёт в handleIncomingMessage | WebSocket слой
3 | Хендлер находит нужный кэш (getMessages / getChats) | chatHandlers.ts
4 | updateQueryData меняет данные в кэше мутацией | RTK Query
5 | Компоненты, использующие useGetMessagesQuery, авто-перерисовываются | React + RTK Query

Важно: Компоненты не знают о существовании WebSocket. Они просто рендерят данные из кэша. Когда кэш меняется — они обновляются.

2️ UI → Server (Отправка сообщения, прочтение)

# Шаг | Что происходит | Кто отвечает

1 | Пользовательское действие (клик, скролл) | Компонент
2 | Оптимистичное обновление: кэш меняется сразу для мгновенного отклика | Компонент / Хендлер
3 | Формируется WS-запрос и отправляется на сервер | sendWS()
4 | Сервер обрабатывает и рассылает broadcast всем участникам | Backend
5 | Клиент получает подтверждение → кэш синхронизируется с сервером | handleIncomingMessage

Зачем оптимистичное обновление: Чтобы пользователь видел отклик мгновенно (0 мс), а не ждал сетевой запрос (100-300 мс).

3️ Server ↔ Cache (Фоновая синхронизация)

# Сценарий: Открыли приложение после перезагрузки, или сообщение было на другой странице.

Механизм |Как работает | Зачем
invalidateTags | Помечает кэш как "устаревший" → при следующем использовании делает refetch | Гарантирует, что данные не застрянут в старом состоянии
keepUnusedDataFor | Хранит неиспользуемый кэш 30-60 секунд | Экономит трафик при быстром переключении между чатами
selectCachedArgsForQuery | Позволяет обновить все страницы сообщений сразу | Решает проблему пагинации при обновлении статуса

Механизм перерисовки (почему UI обновляется сам)

1. handleIncomingMessage вызывает:
   dispatch(chatApi.util.updateQueryData('getMessages', args, draft => {
   draft.results[0].new = false // ← Меняем данные напрямую
   }))

2. RTK Query видит изменение в кэше → помечает подписчиков как "dirty"

3. Компонент с useGetMessagesQuery:
   - Видит, что данные изменились
   - Автоматически запускает ре-рендер
   - Получает новые пропсы

4. React сравнивает виртуальный DOM → обновляет только изменившиеся узлы

Ключевое: Вы не вызываете setState, не передаёте пропсы вручную. Изменение кэша → авто-обновление всех подписчиков.

# Тайминги: Когда пользователь видит изменения

Событие | Время | От чего зависит
Оптимистичное обновление 0 мс | Мгновенно, синхронно с действием
Ответ сервера инициатору 50-200 мс | Скорость сети + обработка бэкенда
Broadcast другим участникам | 100-300 мс | Количество участников + очередь сервера
Фоновый рефетч (invalidateTags) | 200-500 мс |Размер ответа + парсинг

Пользователь видит: Мгновенный отклик → подтверждение через долю секунды. Разница незаметна.

Итог одной схемой
Пользовательское действие
│
▼
[Оптимистичное обновление кэша] → Мгновенный отклик в UI
│
▼
[Отправка WS-запроса] → Сервер
│
▼
[Сервер: валидация + БД + broadcast]
│
▼
[Получение ответа] → [Обновление кэша] → [Авто-перерисовка UI]
│
▼
[Фоновый invalidateTags] → Гарантия актуальности при следующих запросах

Главное: WebSocket — это только транспорт. Логика синхронизации живёт в кэше. Компоненты просто реагируют на изменения. Это делает систему предсказуемой, тестируемой и масштабируемой.
