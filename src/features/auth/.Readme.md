## Вы вводите номер на компьютере.

Берёте свой телефон (тот, чей номер ввели) и звоните на номер, который показан на экране.

Система видит входящий звонок с вашего номера → понимает, что это вы → отправляет подтверждение бэкенду.

Компьютер получает сигнал → автоматически выдаёт токены → вы входите в аккаунт.

🔑 Главное правило: звонить нужно именно с того телефона, номер которого вы указали. Система сверяет номер звонящего с номером в
сессии. Если номера совпали → статус меняется на verified → компьютер автоматически входит.

Никаких кодов вводить не нужно. Факт звонка = подтверждение владения номером. Позвоните, и через 2-5 секунд на компьютере произойдёт вход. 📞✅

🗺️ Архитектурная схема потока

[Браузер] → /start → [Next.js Proxy] → [Бэкенд] → [Plusofon API]
↓ ↓
[UI: номер] ← session_uid, session_secret ← Сессия создана
↓ ↓
Пользователь звонит ───────────────────→ Plusofon шлёт вебхук
↓ ↓
[useReverseCallAuth] polling → /status → Бэкенд ставит status: "verified"
↓ ↓
[claim] → /claim + session_secret → Бэкенд выдаёт JWT (access, refresh)
↓
[handleAuthSuccess] → сохранение токенов → инициализация WS → редирект

1. Разделение ответственности (Clean Architecture)

# Блок | Задача | Почему так

AuthFlow | Маршрутизатор шагов (greeting → phone → reverse_call → chats) | Изолирует UI-флоу от бизнес-логики

ReverseCallAuth | Только UI: отображение номера, статус, кнопка | Компонент не знает про API, только про props

useReverseCallAuth | Инкапсуляция polling, /status, /claim, таймеров | Единый источник правды для сетевого взаимодействия

tokenManager / Redux | Хранение токенов, уведомление подписчиков | Безопасное управление сессией, реакция WS

Next.js /api/proxy/... | CORS-прокси, проброс кук/заголовков, защита эндпоинтов | Фронтенд не стучится напрямую в бэкенд

2.  Пошаговое выполнение потока

🔹 Шаг 1: Создание сессии (/start)

Пользователь вводит номер → POST /api/proxy/.../start/
Бэкенд создаёт сессию в БД, генерирует session_uid, session_secret, call_number
Фронтенд сохраняет данные в стейт (phoneSession) и переходит на шаг reverse_call

🔹 Шаг 2: Ожидание звонка (Polling)

Компонент монтируется → useReverseCallAuth запускает цикл опроса
Каждые poll_interval_seconds (обычно 2 сек) отправляется POST /status/{uid}/
Пока status === "pending" → цикл продолжается
Критично: stopPolling() очищается при размонтировании, чтобы не было memory leaks

🔹 Шаг 3: Вебхук от Plusofon (фоновый процесс)

Пользователь звонит на call_number с того же номера, который указан в сессии
Plusofon фиксирует входящий звонок → отправляет POST на ваш бэкенд
Бэкенд сверяет номер звонящего с session_uid → меняет статус на verified, ставит is_claim_available: true

🔹 Шаг 4: Обнаружение verified и получение токенов (/claim)

Следующий poll получает:
{ "status": "verified", "is_claim_available": true }

Хук сразу вызывает stopPolling() → предотвращает гонку и бесконечные запросы
Отправляется POST /claim/{uid}/ с { session_secret }
Бэкенд валидирует секрет → генерирует JWT → возвращает:
{ "access": "eyJ...", "refresh": "eyJ...", "is_filled": true }

🔹 Шаг 5: Финализация входа (handleAuthSuccess)

Сохранение токенов: tokenManager.setTokens(access, refresh) → записывает в куки/хранилище
Обновление стейта: Redux/Store помечает isAuthenticated: true
Инициализация WS: setupSocket() подключается с ?authorization=<access_token>
Редирект:
is_filled === true → /chats
is_filled === false → /profile/complete

3.  Роль Proxy (/api/proxy/...)

Next.js API-роут выступает как безопасный посредник:
CORS: Фронтенд работает на localhost:3000, бэкенд на другом домене. Proxy убирает ограничения.
Безопасность: Реальный URL бэкенда скрыт от клиента.
Куки/CSRF: Проксирует Cookie, X-CSRFToken, Authorization заголовки.
Прозрачность: Возвращает ответ бэкенда как есть (включая Set-Cookie для HttpOnly токенов).

// Упрощённая логика proxy
const backendRes = await fetch(`${BASE_API}${path}`, {
method: req.method,
headers: { ...reqHeaders, Cookie: req.cookies, 'X-CSRFToken': req.csrf },
body: req.body
});
return new NextResponse(backendRes.body, { status: backendRes.status, headers: backendRes.headers });

4. Управление токенами и сессией

Элемент | Назначение
access_token | Короткоживущий (10 мин). Передаётся в Authorization: Bearer ... к каждому запросу
refresh_token | Долгоживущий (30 дней). Хранится в HttpOnly Secure Cookie. Используется только для обновления access
tokenManager | Кэширует токены в памяти, уведомляет WS и interceptors при изменении
authSlice (Redux) | Хранит isAuthenticated, profile, session. При logout очищает всё

Поток рефреша (если реализован):
401 → tokenManager.refresh() → POST /auth/refresh с refreshToken → новые токены → повтор исходного запроса → WS переподключается.

5.  Инициализация WebSocket

Запускается только после успешного /claim/
Подключение: ws://host?authorization=<access_token>
При 401/4001 от WS → вызывается tokenManager.handleAuthError() → рефреш токена → reconnectWithNewToken()
setWSCurrentUserId(uid) привязывает соединение к профилю для маршрутизации сообщений

6.  Обработка ошибок и таймауты (надёжность)

Сценарий | Механизм

Звонок не прошёл за 2 мин | Бэкенд ставит status: "expired" → poll останавливается → UI предлагает повторить
verified есть, но /claim/ не вызван за 15 мин | Сессия инвалидируется → 409/401 → редирект на /login
Сеть упала во время polling | Retry с экспоненциальной задержкой или fallback на SMS
Размонтирование компонента | useEffect cleanup → clearTimeout → предотвращает setState on unmounted component
Гонка между onSuccess и таймером | stopPolling() вызывается до onSuccess(tokens)
